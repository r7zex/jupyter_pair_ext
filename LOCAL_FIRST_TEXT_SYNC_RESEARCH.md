# Pair Notebook local-first text synchronization research

Date: 2026-09-08

Repository: `r7zex/jupyter_pair_ext`

Investigated baseline: `2f9f815795431b336c64844aedbc82a3f1258479` (`v0.5.20`, current `origin/main` at the start of the investigation)

Scope: root-cause investigation and design research only. This report does not contain the production fix.

## Executive decision

The `v0.5.20` regression is confirmed. Guest typing is displayed immediately, but every host acknowledgement advances only the guest's canonical CRDT and schedules a fresh VS Code projection from that intermediate host state. The projection code creates its render target from a new canonical replica and ignores later optimistic characters that still exist only in the displayed replica. Acknowledging the first of several fast keystrokes can therefore repaint the editor over the later keystrokes. Network delay becomes visible as a delayed copy of the user's own text and can repeatedly undo and reapply the typing tail.

This is not caused by the 500 ms notebook-output cadence. There is no 500 ms text debounce in the new intent path. The visible delay is the host/relay round trip plus the asynchronous `WorkspaceEdit` projection. The defect exists at any non-zero latency and only becomes easier to see as latency rises.

The recommended repair is to restore **local-first Yjs text mutation** while retaining the `v0.5.20` projection-tail quarantine and advisory line presence:

1. A genuine local VS Code edit must update the participant's canonical `Y.Text` synchronously, before network work.
2. The exact Yjs update generated by that local transaction is then transported. Network acknowledgement must never be required to preserve or display the keystroke.
3. Receiving the same Yjs update through another route is safe because Yjs document updates are idempotent. Concurrent inserts, deletes, and newlines are merged by Yjs rather than by whole-cell replacement or a home-grown character diff.
4. The current Session Host remains authoritative for durable storage, execution, snapshots, membership, and host transfer. It must not gate the editor's local text model one keystroke at a time.
5. Selected-line presence remains advisory. A hard line lock or rollback is incompatible with the primary requirement that typing feel like a normal local editor. If a future UI adds an active-line lease, it may warn or decorate, but it must not erase already accepted local typing.

This is both the smallest reliable repair in the current codebase and the architecture closest to JupyterLab's documented collaborative notebook model, which uses Yjs shared models and a network provider rather than a per-keystroke host repaint.

## Reported symptom

The observed behavior is:

1. A guest types normally and the newest character appears immediately.
2. After roughly one network round trip, earlier typed content arrives back from the host.
3. That returned state is rendered into the same editor.
4. Characters typed after the returned operation are temporarily removed, moved, or reapplied.
5. The editor therefore feels as if the user's own input is following them with a delay.

The required stability property is stronger than eventual convergence:

> Once a local edit is visible, an acknowledgement of an earlier local edit must not make any later local edit disappear from the displayed document, even temporarily.

`v0.5.20` does not satisfy this property.

## Exact regression boundary

The current release history establishes a narrow boundary:

- `v0.5.19` points to `bdce97d5341cd9bf92d1398422101fc9790b9e5a`.
- Documentation-only commit `85982327896ea64e3c3c2af4b8adb6935189c747` described the previous projection-tail and line-lock failures.
- `v0.5.20` and `origin/main` point to `2f9f815795431b336c64844aedbc82a3f1258479`.
- `2f9f815` is the functional commit `fix(sync): enforce host-authoritative text updates`.

That commit made three relevant architectural changes:

- `EditorSynchronizer.publishTextChanges()` began offering each editor delta to `SessionRuntime.stageEditorTextIntent()` before mutating the canonical project.
- Guests began keeping the edit only in a private `EditorTextReplica` while waiting for a host operation.
- The runtime began rejecting direct guest-authored canonical text updates and accepting only host-authored canonical updates.

The same commit also added valuable, independent protection against ambiguous `WorkspaceEdit` events and removed destructive selection-derived line locks. Those protections should be retained. The regression comes from coupling the visible editor to intermediate host acknowledgement state, not from the projection-tail quarantine.

## Confirmed root cause

### 1. A guest keystroke is deliberately excluded from the canonical CRDT

For a text or notebook-cell change, `EditorSynchronizer.publishTextChanges()` calculates the displayed baseline and result, then calls the text-intent publisher (`src/vscode/sync.ts:1067-1081`).

When `SessionRuntime.stageEditorTextIntent()` returns `true`, the synchronizer calls `replica.editLocal(changes)` and returns. `editLocal()` mutates only the private replica; it does not merge the generated Yjs update into the canonical `CollaborativeProject` (`src/vscode/editorTextReplica.ts:163-181`).

`SessionRuntime.stageEditorTextIntent()` stores the immutable baseline, delta, result, base revision, and operation ID, sends a `textEditIntent` to the host, and returns `true` (`src/runtime/session.ts:1650-1700`).

After two quick edits, the three relevant states can therefore be:

```text
host canonical:          "a"
guest canonical:         "a"
guest displayed replica: "a!?"
guest VS Code document:  "a!?"
pending intents:         ["a" -> "a!", "a!" -> "a!?"]
```

The immediate display is optimistic, but the authoritative-project observer does not understand that optimistic overlay.

### 2. The host acknowledges an intermediate state

The host accepts the first intent against canonical `"a"`, applies the delta to its own project, and sends a host-authored Yjs update plus an acknowledgement (`src/runtime/session.ts:2392-2479`).

The guest applies that update to its canonical project (`src/runtime/session.ts:2482-2510` or the normal `projectUpdate` handler at `src/runtime/session.ts:2974-3014`). At this instant the state is:

```text
host canonical:          "a!"
guest canonical:         "a!"
guest displayed replica: "a!?"
guest VS Code document:  "a!?"
pending later intent:    "a!" -> "a!?"
```

This state is normal in every optimistic authority protocol. The client must render `canonical + remaining unconfirmed local changes`, not the canonical prefix by itself.

### 3. The projection discards the optimistic suffix

Every canonical text update schedules `EditorSynchronizer.applyText()`. In `renderText()` the synchronizer sees that the VS Code document differs from canonical text. It then creates a **new** `EditorTextReplica` from the canonical project and selects `replica.source()` as the render target (`src/vscode/sync.ts:804-872`).

The existing displayed replica is used only by an early equality check. Its optimistic `"?"` suffix is not composed over the new canonical target. The new target is therefore `"a!"`, and the minimal `WorkspaceEdit` changes the visible document from `"a!?"` back to `"a!"`.

The runtime still has the later intent, but the editor projection has already hidden it. If that later intent is subsequently accepted, another host update can make `"?"` appear again. The user sees exactly the delayed following/rewriting effect from the report.

### 4. Queue rebasing cannot protect the editor

`SessionRuntime.rebasePendingTextIntents()` rebases transport records after rejection (`src/runtime/session.ts:2513-2553`). It has no callback or state provider through which `EditorSynchronizer.renderText()` can obtain the pending overlay. The runtime queue and the displayed replica are two independent optimistic-state implementations.

Consequently:

- transport rebasing may preserve an operation for eventual host acceptance;
- the VS Code document may still be repainted to an earlier host prefix;
- a passing eventual-convergence test does not prove continuous typing stability.

This split ownership is the central design defect.

## Deterministic reproduction

A temporary regression probe was added to the existing fake VS Code boundary, compiled, executed, and removed before this documentation commit.

The probe:

1. initialized a notebook cell to `"a"`;
2. staged local `"!"`, producing `"a!"`;
3. staged local `"?"` before any acknowledgement, producing `"a!?"`;
4. applied only the host update for the first operation to the guest canonical project;
5. waited for the normal text render queue;
6. asserted that the displayed document and displayed replica remained `"a!?"`.

Actual result:

```text
0 passing
1 failing

AssertionError:
an acknowledgement must not repaint over later local typing
actual:   "a!"
expected: "a!?"
```

The current single-operation host-authority test passes because it waits for only one optimistic edit and then acknowledges exactly that complete displayed state. It never leaves a later unconfirmed edit above an earlier acknowledgement. The missing test dimension is therefore **more than one local operation in flight for the same document**.

## Why the perceived delay is about half a second

The `500 ms` constant introduced for `v0.5.19` controls notebook output/execution coalescing. It is intentionally separate from cell text. The `v0.5.20` text intent is sent immediately by `sendPendingTextIntent()`.

The visible lag is instead:

```text
guest keypress
  -> encrypted route to host
  -> host message queue and validation
  -> host CRDT transaction
  -> encrypted project update/acknowledgement to guest
  -> guest message queue
  -> canonical observer
  -> asynchronous VS Code WorkspaceEdit
```

On a direct LAN/WebRTC route this may be short. On a relay, VPN transition, busy extension host, or queued notebook render, it can easily become noticeable. No latency threshold makes the architecture safe: even a 20 ms acknowledgement can overwrite typing produced during those 20 ms.

## Design research

### Option A: pessimistic host-authoritative text

The editor waits for the host before treating a keystroke as accepted.

Advantages:

- simple canonical ownership;
- easy server-side validation and total ordering.

Fatal UX cost:

- visible typing latency equals at least one network round trip;
- host or route loss blocks ordinary editing;
- remote acknowledgements must mutate the active editor continuously.

This option cannot meet the stated goal and is rejected.

### Option B: optimistic authority with a transformed outstanding buffer

CodeMirror documents the standard authority design: each peer tracks the authority version plus local unconfirmed changes. When remote changes arrive, the peer removes acknowledged local changes and transforms remote changes across the remaining local changes, while transforming those remaining local changes for resubmission. ProseMirror exposes the same core responsibilities through `sendableSteps()` and `receiveTransaction()`.

This model can meet the goal, but only if the displayed editor state is the primary optimistic state and remote changes are applied **through** its outstanding-change buffer. Repainting a plain canonical prefix is forbidden.

Pair Notebook `v0.5.20` implements the server queue half of this model but not the editor-state half. Completing it correctly would require:

- one ordered outstanding buffer shared by runtime and editor projection;
- explicit acknowledgement identity on every echoed operation;
- transform/rebase mappings for insert/delete/replace operations;
- selection, composition, undo, and redo mapping through every transform;
- atomic handling of multi-change VS Code events;
- reconnect history or snapshot recovery;
- strong property and stress tests for every interleaving.

The current `diffChars(..., { timeout: 25 })` mapping is useful as bounded recovery, but it is not an editor-native OT implementation and should not become the normal per-keystroke conflict engine.

This option is viable but is larger and riskier than using the Yjs shared text model already present in the product.

### Option C: local-first Yjs shared text with host persistence

Yjs document updates are documented as commutative, associative, and idempotent: they may arrive in any order and be applied multiple times. Yjs providers distribute updates after the local shared type changes. JupyterLab's collaborative notebook implementation uses Yjs shared models and a provider that synchronizes those models to other clients.

For Pair Notebook this means:

```text
VS Code local edit
  -> displayed EditorTextReplica transaction
  -> merge the exact Yjs delta into local canonical project
  -> transport the resulting project update
  -> host and peers apply the same idempotent update
  -> host persists merged canonical state on its existing debounce
```

The local editor never waits for transport, and an echoed update cannot recreate a second character because it carries the same Yjs identity. Concurrent operations are integrated by Yjs at the shared-text level. The host remains the durable and execution authority without being a synchronous keystroke gate.

This is the recommended option.

### Option D: full-cell snapshots or last writer wins

Sending the complete cell after each change is simple, but concurrent edits become whole-cell conflicts. A late snapshot can erase unrelated local work, move the cursor, retrigger formatters, and consume bandwidth proportional to the cell size per keystroke.

This is rejected except as a bounded repair snapshot after a verified state/digest failure.

### Option E: hard selected-line locks

A hard lock makes a line number or selection an authorization boundary. It is fragile because line numbers change as collaborators insert/delete newlines, presence can be stale, and VS Code does not identify the author of every text event. Pair Notebook previously demonstrated destructive rollback and adjacent-line false positives from this policy.

Yjs relative positions are appropriate for cursor/highlight placement because they remain attached to shared content as remote edits change numeric offsets. They are not a reason to reject text.

Decision:

- keep selected-line highlighting as ephemeral awareness;
- do not reject, restore, or roll back a local edit because another participant selects the line;
- let Yjs merge true simultaneous same-line edits;
- optionally add a future short-lived “actively typing here” decoration, but never make it a data-loss path.

## Why this is closer to the desired Colab experience

Google's public Colab page promises an integrated collaborative notebook experience, sharing, and version management. It does not document the internal synchronization algorithm, acknowledgement protocol, OT implementation, CRDT choice, or locking policy. Therefore this report does not claim that Colab uses Yjs or the exact algorithm proposed here.

The comparison is limited to the observable product requirement: local typing should not wait for a remote round trip or be repainted by a stale acknowledgement.

JupyterLab is the stronger technical analogue because its implementation is public and notebook-specific. Its documented real-time collaboration uses Yjs shared models, and the JupyterLab integration explicitly replaced bespoke editor/model synchronization with a shared Yjs model and a provider.

## Concurrent same-cell and newline behavior

The required unit of collaboration is the stable notebook cell's `Y.Text`, not a whole serialized `.ipynb` file and not a mutable line number.

For two users editing one cell:

1. each local editor transaction is applied immediately to its local replica/canonical `Y.Text`;
2. each generated Yjs update is broadcast immediately;
3. every peer eventually applies the union of those updates;
4. duplicate routes and replay are harmless because the updates are idempotent;
5. cursors and active-line highlights use Yjs-relative anchors rather than raw offsets;
6. outputs, execution, metadata, and structure keep their existing semantic scopes and must not trigger a full cell-text replacement.

For simultaneous newlines at the same logical position, both inserts are retained according to Yjs's deterministic item ordering. The exact visual order can depend on the CRDT identities, but every peer must converge to the same text. No participant's complete cell snapshot may overwrite the other insertion.

The design does not promise that all concurrent source edits produce semantically valid Python. It promises preservation, convergence, and absence of silent rollback. Syntax review remains a human collaboration concern.

## Required implementation boundaries

The repair should change only text authorship/transport behavior and related tests/documentation:

- keep the existing `EditorTextReplica.edit()` path that merges the exact local Yjs update into canonical state;
- stop routing normal editor typing through `stageEditorTextIntent()`;
- allow authenticated guest text `projectUpdate` frames to participate in the same CRDT convergence path as host updates;
- stop treating a non-host local text project update as an error requiring host repair;
- make closed text-file watcher changes follow the same local-first path;
- retain `v0.5.20` projection-event capture, delayed-tail quarantine, stale-render guards, and advisory line presence;
- keep host-only persistence, execution, snapshots, and explicit host transfer unchanged;
- retain bounded state-vector reconciliation as the repair mechanism;
- advance the protocol boundary if mixed `v0.5.20`/new-release behavior would otherwise allow two text-authority models in one session.

The initial repair should not introduce a new editor framework, server, database, or text data type.

## Non-negotiable invariants and regression matrix

### Local responsiveness

- After each local event returns, VS Code text, displayed replica, and local canonical `Y.Text` contain that event.
- No network acknowledgement is required for the local character to remain visible.
- A delayed echo of any prefix of the local update stream is visually idempotent.
- Ten or more local edits may remain in flight without any intermediate rollback.

### Convergence

- Host and all peers converge after exchanging the same update set in any order.
- Replayed updates do not duplicate characters or newlines.
- Concurrent insert/insert, insert/delete, delete/delete, replace/replace, paste, line split, and line join cases converge.
- Same-position concurrent newlines retain both operations and produce identical text on every peer.
- A state-vector repair after dropped/reordered frames converges without a full editor rollback.

### VS Code projection boundary

- Split, reshaped, multi-event, version-jump, and hidden-target `WorkspaceEdit` echoes are never republished as local input.
- A genuine local edit before, during, or after a remote render is preserved.
- Delayed formatter/notebook-model tails remain quarantined.
- A stale queued render cannot overwrite a newer local version.
- Text remains prioritized over the 500 ms output/execution render cadence.

### Notebook isolation

- Cell text updates use stable cell IDs and `cellText` scope.
- Editing one cell never replaces a neighboring cell, output, execution summary, metadata, or notebook structure.
- Output-only updates do not invalidate text replicas or move the cursor.
- Closed-file synchronization does not reintroduce a host-acknowledgement loop.

### Presence and selection

- Remote active-line anchors follow insertions/deletions through Yjs-relative positions.
- Presence remains ephemeral and advisory.
- A stale/disconnected selection cannot reject or roll back text.

### Lifecycle and recovery

- Route loss may delay distribution but not local typing.
- Reconnect exchanges state vectors and converges queued local Yjs updates.
- Disposal, session end, and host transfer cancel stale renders and never revive destroyed state.
- The host materializes the final merged CRDT before execution, transfer, and final persistence barriers.

## Acceptance gates

Before release:

1. Add a regression that fails on `v0.5.20` with `a -> a! -> a!?` and an acknowledgement/echo of only `a!`.
2. Add same-cell multi-peer interleaving probes, including simultaneous same-offset newlines and reverse delivery.
3. Run focused editor/runtime/network suites.
4. Run the complete JavaScript artifact gate.
5. Run the Python bridge suite.
6. Run the production dependency audit.
7. Verify the generated VSIX and complete ZIP, tag commit, checksums, and GitHub Actions release.

Automated tests can prove source-level convergence, event containment, packaging, and protocol behavior. They do not prove installed VS Code UX or physical two-computer behavior. A final manual acceptance check should type continuously on both machines under direct and forced-relay routes and confirm that no local character follows or rolls back.

## Evidence limits

- The deterministic probe proves the Pair Notebook repaint defect. It does not measure the user's exact physical route latency.
- The source path proves that a host round trip can cause the symptom. It does not claim that the output cadence is the delay source.
- Public Colab material does not reveal Colab's synchronization internals, so Colab is used only as a UX benchmark.
- JupyterLab/Yjs and CodeMirror/ProseMirror show two established solution families. They do not remove the need to test Pair Notebook's VS Code boundary, notebook scoping, transport, and lifecycle behavior.
- Installed VS Code and two-computer acceptance remain unverified until performed on the packaged release.

## Stop condition

Research stopped when all consequential decision slots had direct evidence:

- the regression was reproduced against `v0.5.20`;
- the exact editor/runtime ownership gap was localized;
- the apparent 500 ms delay was separated from the output cadence;
- established optimistic-authority and CRDT alternatives were compared from primary project documentation;
- the recommended local-first Yjs path was mapped to existing Pair Notebook components;
- concurrency, newline, projection, lifecycle, and release acceptance requirements were specified;
- Colab's undocumented internals were explicitly bounded rather than inferred.

Additional generic collaboration examples would not materially change the architecture decision.
