# Pair Notebook 0.6.16 verification

Cause: VS Code saves a dirty notebook before closing its tab. After Leave, deletion or epoch retirement, 0.6.15 preserved archives but the original `pair-vps` working copy still used a server-only save provider. Save failed with `Connect to a server project first`, preventing a normal Save-and-close operation.

Fix: detached notebook URIs now have a durable local backing file under `globalStorage/pair-notebook.pair-notebook/persistent-detached/`. Read, stat and Save for that exact URI use local recovery. Local saves clear VS Code's dirty state without sending a server write or recreating a deleted file. Queues and recovery filenames include the full URI, separating epochs and editor attachments. A fresh server editor receives a separate attachment URI when an older local recovery uses the same epoch. Existing dirty models from a previous extension host can be adopted locally on Save, including after connection restoration fails authorization. Unknown disconnected URIs still fail, and server authorization is unchanged.

Verification: 94 focused Linux transport/provider/synchronizer/compatibility tests passed; TypeScript and scoped ESLint passed. A real Windows VS Code client used an isolated loopback Linux server and two epochs of one notebook alongside a same-name local Jupyter file. Both detached epochs saved and closed. The test clicked Save in the actual dirty-tab close dialog using Windows computer-use automation, verified recovery contents and byte-identical server/local files, reconnected to a separate current editor, and saved/closed a dirty model retained across provider replacement with no active connection.

Limits: the complete release matrix and a long soak were not rerun. The provider-replacement probe deliberately unregistered/re-registered the filesystem and produced transient ENOPRO warnings for auxiliary agent-discovery paths; the detached notebook Save-and-close checks succeeded. No production server update, source execution or TLS/package-install repair was performed. The pip certificate error visible in the user's screenshot is a separate server environment issue.

This closing fix is client-side: install the VSIX and restart the Extension Host or reload the window while preserving dirty buffers. Original journals and versioned recovery archives remain intact. Successful Save on a detached tab means local recovery, not server publication; an information message explains this when it detaches.
