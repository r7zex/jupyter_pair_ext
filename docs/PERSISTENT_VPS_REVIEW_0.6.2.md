## Воспроизводимые дефекты и исправления

1. **Повторная публикация отменяла rename.** Terminal report публикует новый `result.txt` (version 0), затем падает до final receipt. Пользователь переименовывает файл в `renamed.txt`; retry или новый server создавал `result.txt` снова. Два новых HTTP сценария падали на 0.6.1 (`200` вместо `404`). Теперь publication ID сохраняется вместе с изменением в одном workspace manifest; последующие rename/delete не отменяются. Receipts очищаются только после durable final receipt. Отдельные storage fault tests проверяют отказ до commit и потерю acknowledgement после commit. Это не отдельная неатомарная запись progress после файла. [Storage](../src/vps/persistentStorage.ts), [merge](../src/vps/persistentServer.ts), [regressions](../test/persistentSession.test.ts).
2. **Consent был недоступен при locked switch.** Owner выбирает свою CPU/GPU; member не имеет consent, а `select` отвергал даже этот же target. Два новых policy сценария падали на 0.6.1. Exact current-target запрос теперь не меняет selection authority, owner baseline, generation или pending owner selection. Другая машина/GPU по-прежнему запрещена. Поздний approve не возвращает прежнее устройство; revoke проверяется перед claim. UI предлагает `Request access`, с fencing обоих диалогов и позднего RPC. [Policy](../src/vps/persistentCompute.ts), [UI](../src/vscode/persistent.ts), [tests](../test/persistentCompute.test.ts).
3. **CI не доходил до упаковки.** [Run 38398564228](https://github.com/r7zex/jupyter_pair_ext/actions/runs/38398564228) на `d7cfdb…` завершился `Cannot find module './persistentServer'`: reference integration замораживал четыре прежних модуля. Теперь retained/hash evidence включает все десять runtime dependencies; оба настоящих reference сценария прошли локально. [Harness](../test/persistent_reference_integration_test.py).
4. **Сборки не доказывали чистый SHA.** Server всегда сообщал `localChangesIncluded: true`, VSIX не имел source commit manifest. Теперь compile создаёт provenance с commit/dirty и hash runtime; packaging сверяет VSIX bytes, standalone smoke — commit/dirty и каждый bundled file. Для финальной поставки сборки создаются после commit из чистых tracked sources. [Provenance](../scripts/build-provenance.mjs), [VSIX check](../scripts/make-artifacts.mjs), [server smoke](../test/persistent_server_archive_smoke.mjs).
5. **Kernel controls раздували durable metadata.** `kernelControl` копировал произвольные поля `command` из RPC, ограничивал число controls (128), но не их совокупные bytes; terminal records сохраняли stdin. Два новых сценария воспроизвели лишний `unrelatedPayload` в worker claim и принятие четвёртого 64 KiB input. Теперь передаются только command/requestId/value, совокупный лимит равен 256 KiB, а terminal report очищает controls атомарно с execution receipt. Это предотвращает накопление больших payload/input в session metadata и archive. [Host](../src/vps/persistentServer.ts), [API regressions](../test/persistentSession.test.ts).
6. **Retry/fsync не гарантировал успешное сохранение.** После полного blob write и неуспешного fsync повтор использовал существующие bytes без нового file/directory fsync. Частично записанный unreferenced blob блокировал retry до restart. Кроме того, общий atomic writer игнорировал Linux directory-sync `EACCES/EPERM`, а sync error после rename мог попадать в rename fallback. Четыре fault scenarios падали на прежнем коде. Теперь reuse синхронизирует файл и каталог; только unreferenced regular orphan восстанавливается, published corruption и links остаются fail-closed; Linux metadata sync errors возвращаются вызывающему, не маскируются как успешное сохранение или неудачный rename. Ветка совместимости non-Linux сохранена (её unit simulation не является native Windows/macOS испытанием). [Storage](../src/vps/persistentStorage.ts), [writer](../src/core/atomicFile.ts), [blob tests](../test/persistentStorage.test.ts), [directory tests](../test/persistentAtomicFile.test.ts).
7. **Несогласованные wire limits блокировали worker.** Host допускает command до 16 MiB, agent читал response до 10 MiB. Реальный HTTP тест с Public notebook меньше 4 MiB воспроизвёл accepted claim больше 10 MiB, который agent не мог получить даже как recoverOnly: глобальный VPS slot оставался занят. Лимит ответа теперь 20 MiB и включает bounded controls; command/source/snapshot/outputs сохраняют собственные меньшие квоты. Новый integration проверяет реальные Host → Transport bytes и явное освобождение claim; этот отдельный wire сценарий не запускает kernel и не считается CUDA/isolation proof. [Agent transport](../scripts/pair-notebook-session-agent.py), [HTTP regression](../test/persistent_session_cpu_integration_test.py).
8. **Потеря namespace была не видна, rename блокировал capacity.** Agent посылал `kernelState`, но controller игнорировал сообщение: restart agent с прежней server generation не показывал сброс RAM. Переименование Public notebook оставляло старый kernel под прежним path; при `--max-kernels 1` новый notebook не запускался. UI теперь показывает kernel-state notices, а валидный rename Public notebook/содержащей его папки меняет kernel generation перед manifest publication. Это явный reset, не миграция Python objects; уже принятый код не отменяется. Настоящий Jupyter regression воспроизвёл capacity failure, затем подтвердил исполнение после rename, один kernel и новый counter `1`. [Controller](../src/vscode/persistent.ts), [Host rename](../src/vps/persistentServer.ts), [real CPU regression](../test/persistent_session_cpu_integration_test.py).
9. **Поздние действия UI затрагивали другое соединение.** Manage/settings/lifecycle, share/revoke, upload и recovery могли использовать новую connection после старого диалога; старый leave ACK очищал её. Поздний attach heartbeat также заменял уже готовое новое соединение. Шесть UI scenarios воспроизвели эти ошибки на прежнем controller. Действия/ответы теперь закреплены за исходным connection, upload повторно проверяет его после чтения local bytes; leave очищает только свою connection; attachment использует поколения и сериализованное сохранение credentials, сохраняя старый owner credential без смены нового active workspace. [Controller](../src/vscode/persistent.ts), [UI regressions](../test/persistentClient.test.ts).

Комментарий PR о восстановлении удалённого файла перепроверен: обычный API `remove` уже меняет privacy epoch и блокирует старый merge. Однако публичный rename не меняет epoch и реально воспроизводил дефект. Исправление защищает обе операции через atomic publication receipts, а не предполагает отсутствие удалённого файла исходным version 0.

## Незакрытая приёмка

- Серверный CRDT/одновременное несохранённое редактирование и наблюдение локальных папок; сейчас синхронизация при сохранении/ручном upload.
- Windows/macOS isolation и owner-only Private kernels отсутствуют в реализации.
- Реальная NVIDIA/CUDA и два физических executor, включая CPU/GPU переключение.
- Два настоящих VS Code: установка финального VSIX, virtual workspace reload, конфликт, consent/revoke и recovery; ручной P2P.
- Целевой VPS `192.0.2.10`: non-root production isolation, ограничения RAM/CPU/disk, доверенный TLS/renewal, systemd reboot и backup restore. SSH credentials отсутствуют; VPS не изменялся.
- Длительный persistent-session soak и измеренная доступность. Короткий background-reference recovery не доказывает годовой uptime или многодневную Session Host нагрузку.
- Session discovery/invite URL и бесконечное хранение receipts в пределах фиксированного диска требуют дальнейшей реализации/эксплуатационного решения.
